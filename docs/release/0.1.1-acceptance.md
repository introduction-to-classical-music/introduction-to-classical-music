### 3.2 差异与原因

1. **libraryId/createdAt 不同**：安装包种子在打包阶段（01:26）由一次 bootstrap 生成，发布快照在之后（01:52）由 `export-default-library` 从另一个干净构建中导出。每次 bootstrap 都会生成新的 library UUID 与时间戳，因此两者 ID 不同属于生成流程差异，而非内容差异；安装版首启把安装包种子复制到 AppData，AppData 与安装包种子完全同 ID。
2. **构建 meta `appVersion=0.1.0`（产品 0.1.1）**：两份对象均由 W4 之前的构建代码产生，旧构建把 `appVersion` 写死为 0.1.0。W4（`d13c585`）起构建 meta 使用真实应用版本；**已发布 0.1.1 二进制不修改、不重打包**，因此其种子 meta 仍为 0.1.0。
3. **内容一致**：两份快照实体计数均为 0，均含同一篇使用手册；内容层唯一差异是文章时间戳。`release-default-library/v0.1.1/snapshotDigest=80bdebed…` 是**发布快照**的完整性封条（45 文件），W10a 规范化前后不变。
4. **旧种子站点的已知旧缺陷**：W8b 观察到已发布 0.1.1 首启种子站点仍含 Pages 前缀（F09 旧行为）且 meta 0.1.0；这些只在**未来构建**中由 W4/W10b 修复，已发布安装包行为不变。

### 3.3 结论与后续建议

- W7a 判据“安装包种子 libraryId 与发布快照清单一致（或明确记录差异原因）”：**以本记录明确差异原因满足**；发布 provenance 以 `release-manifest.json` + `snapshotDigest` 为准，不以 library UUID 相等作为完整性判据。
- 已增强 `scripts/export-default-library.mjs`：导快照前校验构建 meta 的 `appVersion` 与发布版本一致（拒绝 0.1.0 旧构建，提示重新 `npm run build`），并在新 manifest 中记录 `buildMetaAppVersion`/`buildMetaBuiltAt`；测试见 `tests/unit/library-release-manifest.test.ts`。
- 建议 0.1.2 起在打包流水线中**先构建一次默认库，再由同一产物生成安装包种子与 release-default-library 快照**，并在 CI 中比对两者 libraryId/内容，从流程上消除该差异。
